# Review/Tests: типовые сценарии работы

Сценарии проверки корректной работы протокола S/KEY в проекте.

## Пререквизиты
- Сервер запущен: `python3 server.py`
- Подключение к серверу через `telnet localhost 12345` или `nc localhost 12345`
- Клиент доступен: `python3 client.py`

## 1) Успешная регистрация и вход (правильный пароль)
1. На сервере: `INIT alice` → получите `REG_ID`, `SEED`, `N` (например, `N=10`, `SEED=1A2B`).
2. На клиенте посчитать `v_n` (6 слов):
   - `python client.py --secret "pass phrase" --seed 1A2B --seq 11` (11, потому что 10 - это n, считаем для n + 1 = 11)   
   - Вывод из 6 слов — это `v_n`.
3. Завершить регистрацию:
   - `INIT_FINAL <REG_ID> 10 <эти_6_слов>` → сервер ответит OK и покажет челлендж `10 1A2B`.
4. На клиенте посчитать ответ `v_{n-1}`:
   - `python client.py --secret "pass phrase" --seed 1A2B --seq 10`
5. Войти:
   - `AUTH alice <шесть_слов>` → сервер вернёт `OK`, `Remaining` уменьшится на 1, выдаст новый челлендж `9 1A2B`.

Ожидаемое: каждое успешное `AUTH` уменьшает `seq` на 1, хранит полученное значение как новый `last_hash`.

## 2) Ложный пароль (неверный секрет/seed/seq)
1. После успешной регистрации возьмите неверный секрет ИЛИ неверный `seed` ИЛИ неверный `seq` (например, `seq=9` при челлендже `10`).
2. Посчитать 6 слов и отправить:
   - `AUTH alice <неверные_6_слов>`

Ожидаемое: сервер отвечает `FAIL`, `seq` не изменяется, челлендж остаётся прежним.

## 3) Штатные ситуации протокола
- `STATUS alice` показывает: `Seed`, `Remaining/Total`, `Challenge: n seed`.
- `LIST` показывает пользователей и число оставшихся шагов (`seq`).
- Регистрация хранится как «ожидающая» до завершения (`INIT_FINAL`) или истечения TTL (~5 минут). Просроченный `REG_ID` станет недействительным.
- Повторное `INIT` на уже существующего пользователя → `User already exists`.

## 4) Нештатные ситуации и обработка ошибок
- `INIT_FINAL` с некорректными словами (не 6 слов / нет в словаре / ошибка КС) → `Invalid password: ...`.
- `AUTH` с некорректными словами → `FAIL`.
- `INIT_FINAL` с неверным `REG_ID` → `Invalid or expired reg_id`.
- `INIT_FINAL` с неверным `N` → `N mismatch`.
- `AUTH` для несуществующего пользователя → `FAIL`.

## 5) Попыток входа больше, чем задано сервером (исчерпание seq)
- Сервер хранит цепочку длиной `N`. Каждая успешная аутентификация уменьшает `seq` на 1.
- Когда `seq` достигает 0, дальнейшая аутентификация невозможна (нужен `v_{-1}`, которого не существует). Сервер продолжит выдавать `Challenge: 0 seed`, но любой `AUTH` будет заканчиваться `FAIL`.
- Решение: повторно инициализировать пользователя с новым `N`/`seed`/секретом:
  - Через сервер: `INIT ...` → `INIT_FINAL ...`
  - Или офлайн: `python keyinit.py <user> "<phrase>" <iterations> [seed]`

## Повторное использование OTP
- Повторная отправка уже использованного OTP не даст доступ: сервер обновляет `last_hash` на принятое значение, поэтому повторное значение не удовлетворит проверке `f(value) == stored`.
- Формат ввода/вывода — только 6 слов из словаря.
