# Lab4 — Oakley Main Mode (RFC 2412)

Лабораторная работа посвящена протоколу Oakley (RFC 2412/2409) и демонстрирует **Main Mode (режим 1) с аутентификацией по заранее разделяемому ключу**. Реализация построена в духе предыдущих лабораторных: есть TCP‑сервер (Responder) и клиент (Initiator), обменивающиеся четырьмя сообщениями `MSG1…MSG4`, которые повторяют структуру примера из спецификации. Форматы сообщений упрощены и передаются в JSON, что позволяет легко наблюдать все поля и проверять корректность вычислений.

## Состав проекта

- `oakley_groups.py` — стандартизованные MODP‑группы Oakley 1 (768 бит) и 2 (1024 бита).
- `oakley.py` — ядро протокола: генерация Nonce и Cookie, расчёт DH‑значений, функций PRF (HMAC-SHA1) и вспомогательные сериализаторы SA/ID payload.
- `server.py` — Responder: ожидает `MSG1`, отвечает `MSG2`, проверяет `HASH_I`, формирует `HASH_R` и публикует итоговую сводку.
- `client.py` — Initiator: стартует обмен с `MSG1`, проверяет `HASH_R`, выводит общий секрет и производные ключи.

## Выбранный режим и структура сообщений

Mode 1 (Main Mode) выполняет аутентифицированный обмен Диффи — Хеллмана в шести ISAKMP‑сообщениях. В учебной реализации они сведены к четырём JSON‑пакетам в следующем порядке:

| Сообщение | Содержимое | Назначение |
|-----------|------------|------------|
| `MSG1` (I→R) | `HDR(CKY-I, CKY-R=0)` + `SA`, `KE`, `Ni` | Предложение параметров, публикация `g^x_i`, генерация Cookie инициатора и Nonce `Ni` |
| `MSG2` (R→I) | `HDR(CKY-I, CKY-R)` + `SA`, `KE`, `Nr` | Выбор параметров, ответный ключ `g^x_r`, Cookie респондента и Nonce `Nr` |
| `MSG3` (I→R) | `HDR` + `IDii`, `HASH_I` | Аутентификация инициатора (PSK) и подтверждение `SA` |
| `MSG4` (R→I) | `HDR` + `IDir`, `HASH_R` | Аутентификация респондента, завершение обмена |

Дополнительно сервер отправляет `RESULT` (не часть стандарта) со сводкой: общий секрет `g^xy` и материал `SKEYID`, `SKEYID_d`, `SKEYID_a`, `SKEYID_e`.

### Поля и формулы

- **Cookie (`CKY-I`, `CKY-R`)** — 64-битные случайные значения, защищающие от DoS (секция 5 RFC 2412).
- **Nonce (`Ni`, `Nr`)** — 128-битные случайности, входящие в PRF и предотвращающие повторное использование старых ключей.
- **SA payload** — предложения по алгоритмам: `ENCRYPTION=3DES-CBC`, `HASH=SHA-1`, `AUTH=PSK`, `GROUP=MODP-1024`, время жизни 8 часов.
- **KE payload** — открытые значения DH: `Y_i = g^{x_i} mod p`, `Y_r = g^{x_r} mod p`.
- **ID payload** — тип `ID_IPV4_ADDR` с адресами по умолчанию `192.168.50.10/1`.
- **Хеши аутентификации** (формулы из секций 4.1 и 4.5 RFC 2409):
  - `SKEYID = prf(PSK, Ni | Nr)`
  - `SKEYID_d = prf(SKEYID, g^xy | CKY-I | CKY-R | 0)`
  - `SKEYID_a = prf(SKEYID, SKEYID_d | g^xy | CKY-I | CKY-R | 1)`
  - `SKEYID_e = prf(SKEYID, SKEYID_a | g^xy | CKY-I | CKY-R | 2)`
  - `HASH_I = prf(SKEYID, g^{x_i} | g^{x_r} | CKY-I | CKY-R | SA | IDii)`
  - `HASH_R = prf(SKEYID, g^{x_r} | g^{x_i} | CKY-R | CKY-I | SA | IDir)`

В учебной реализации SA и ID сериализуются в канонический JSON (фактический ISAKMP‑формат TLV опущен), поэтому обе стороны вычисляют хеши из одинаковых байтовых последовательностей.

## Защитные механизмы

- **Диффи — Хеллман** с MODP‑группой Oakley #2 (1024 бита) обеспечивает стойкость к пассивному перехвату.
- **Cookies** не позволяют инициировать дорогой DH до подтверждения адреса клиента.
- **Nonces + PRF** гарантируют свежесть и уникальность `SKEYID`, даже при повторном использовании PSK.
- **HASH_I / HASH_R** связывают все параметры обмена (SA, ID, Cookies, публичные ключи) и тем самым защищают от атак «man-in-the-middle» при условии, что PSK совпадает у обоих участников.
- **Ротация ключей**: после каждого обмена генерируются новые приватные экспоненты и nonces.

## Запуск

1. **Responder**:
   ```bash
   python3 lab4/server.py --host 127.0.0.1 --port 12000 --psk lab4-shared-secret --verbose
   ```
2. **Initiator** (отдельным процессом/терминалом):
   ```bash
   python3 lab4/client.py --host 127.0.0.1 --port 12000 --psk lab4-shared-secret --verbose
   ```

Ключ и идентификаторы можно переопределить флагами `--psk`, `--identity`. Для демонстрации ошибок запустите клиент с неверным `--psk`: сервер вернёт JSON `ERROR`, а клиент закончит работу с сообщением «Handshake failed».

## Допущения и упрощения

- Реальные ISAKMP payload (TLV-структуры, padding, поля Next Payload) заменены на канонический JSON.
- Основной режим Oakley предполагает шесть сообщений; здесь объединены пары 1/2 и 5/6, оставаясь логически верными спецификации.
- Используется только PSK-аутентификация; режимы с цифровой подписью/сертификатами не реализованы.
- PRF = HMAC-SHA1, как в RFC 2409. В реальных системах рекомендуется переход на более современные алгоритмы (например, SHA-256).
